Module One

How Claude works

Next-tokenThinking & effortThe APICost
⚙ Mechanism

One token at a time

Claude is autoregressive: it reads all the context, then predicts a probability for every possible next token, emits one, appends it, and repeats. There is no plan stored anywhere — the growing text is the state.

This is why it can "change its mind" mid-sentence, why output is billed per token, and why thinking out loud (reasoning) improves answers — more tokens = more computation.
▸ Leverage · the intelligence dial

Adaptive thinking + effort

Modern Claude decides when and how much to think on its own. You no longer set a token budget — you set an effort level, and Claude allocates reasoning within it.

Rule of thumb: high for most serious work, xhigh for hard coding/agentic tasks, low for cheap/fast subtasks.
client.messages.create( model="claude-opus-4-8", max_tokens=16000, thinking={"type":"adaptive"}, output_config={"effort":"high"}, # low | medium | high | xhigh | max messages=[{"role":"user", "content":"Plan the migration."}], )
◆ Concept · the one endpoint

Everything is /v1/messages

Tools, vision, caching, structured output — all features of a single stateless endpoint. You send system + a messages list; you get back content blocks + usage + stop_reason.

Content is a list of typed blocks — check block.type (text / thinking / tool_use) before reading it.
resp = client.messages.create( model="claude-opus-4-8", max_tokens=1024, system="You are a support agent.", messages=[ {"role":"user", "content":"..."}, {"role":"assistant", "content":"..."}, {"role":"user", "content":"..."}, ], ) resp.stop_reason # end_turn | tool_use | max_tokens ... resp.usage # input_tokens, output_tokens
▸ Leverage · know the bill before you send

Cost is tokens × price

Estimate before sending with count_tokens — never tiktoken (that's OpenAI's tokenizer and undercounts Claude badly).

Opus 4.8 = $5 / 1M input. A 200K-token doc ≈ $1.00 just to read it once — before any output.
# exact count for THIS model n = client.messages.count_tokens( model="claude-opus-4-8", messages=messages, ).input_tokens est = n * 5 / 1_000_000 # $/1M input print(f"~${est:.4f} to send") # after the call, the truth: resp.usage.input_tokens resp.usage.output_tokens
✕ Pitfalls · know the edges

Powers — and how to patch the limits

✓Leans on

  • Language, code, reasoning, vision
  • Long-context reading (up to 1M tokens)
  • Tool use & structured output
  • Following clear instructions faithfully

!Limit → mitigation

  • Hallucination → ground with context + "say if unsure"
  • Knowledge cutoff → give tools / web search
  • No memory → resend history / persist facts
  • Non-deterministic → validate & retry, don't assume exactness
Every limitation has an engineering answer — the rest of this deck is those answers.

Module Two

Prompting, engineered

RolesPRECISEXMLFew-shotStructured outputChaining
⚙ Mechanism · who has authority

System > User, by design

The system prompt sets standing rules and persona and carries more weight than user turns. User and assistant messages alternate to form the conversation. The model is trained to let system-level instructions win.

Put stable rules in system; it also makes the prompt cacheable (Module 3).
system = """You are a senior support engineer. Be concise. Never reveal internal order IDs.""" messages = [ {"role":"user", "content":"Where's order A-19?"}, ] # assistant reply is appended, # then the next user turn, ...
▸ Leverage · a repeatable recipe

Vague → PRECISE

✕Before

"Summarize this feedback."

Ambiguous length, format, audience → inconsistent output you can't parse.

✓After

P: You are a product analyst. R: 3 themes with a severity 1–5. E: [one worked example] C: <feedback>…</feedback> I: Only use the feedback given. S: Return JSON {theme,severity}. E: If none, return [].

Each letter removes one degree of freedom the model would otherwise guess.
⚙ Mechanism · fences the model can see

Tags remove ambiguity

Claude is trained on lots of structured text, so explicit tags like <document> and <instructions> give it clean boundaries — it stops confusing your data for your instructions.

Especially valuable when user-supplied content could contain text that looks like an instruction (prompt-injection defense).
<instructions> Extract every action item. </instructions> <transcript> {{ meeting_text }} </transcript> <format> One bullet per item: owner — task </format>
▸ Leverage · teach by example

Show, don't tell

Two or three worked input → output pairs teach format and edge cases faster than a paragraph of rules. Zero-shot = none, one-shot = one, few-shot = several.

Put examples as prior user/assistant turns, or inside <example> tags. Cover the tricky case, not just the happy path.
<example> input: "gr8 servce!!" output: {"sentiment":"pos", "typo":true} </example> <example> input: "it's fine i guess" output: {"sentiment":"neutral", "typo":false} </example>
▸ Leverage · guarantee the shape

Don't beg for JSON — enforce it

The modern way to get machine-parseable output is structured outputs: pass a JSON schema and the response is constrained to match — no more regex-scraping prose. (The old "prefill the assistant turn" trick now errors.)

messages.parse() validates against a Pydantic model and hands you a typed object.
from pydantic import BaseModel class Contact(BaseModel): name: str email: str wants_demo: bool resp = client.messages.parse( model="claude-opus-4-8", max_tokens=1024, messages=[{"role":"user","content":text}], output_format=Contact, ) c = resp.parsed_output # typed & valid
⚙ Mechanism · one job per call

Split the task, gain reliability

A giant "do everything" prompt fails in hard-to-debug ways. Break it into a chain where each step's output feeds the next — each is small, testable, and independently cacheable.

Step 1
Extract facts
→
Step 2
Summarize facts
→
Step 3
Format as email
Bonus: you can use a cheaper model (Haiku) for the easy steps and Opus only for the hard one.
✕ Pitfalls

What beginners get wrong

✕Avoid

  • SHOUTING "CRITICAL: YOU MUST" — modern Claude over-triggers on it
  • Dumping the whole knowledge base into every prompt
  • Prefilling the assistant turn to force format (now 400s)
  • Relying on prose parsing instead of a schema

✓Instead

  • State each rule once, plainly
  • Load only the context this task needs
  • Use output_config.format / parse()
  • Give examples of the edge case, not the obvious case

Module Three

Context, managed

TokensWindowCachingLifecycle
⚙ Mechanism

Not words — tokens

Tokens are sub-word pieces (~¾ word in English, but code and non-English split much finer). The tokenizer is model-specific — the same text costs different token counts on different Claude models.

Never estimate Claude tokens with tiktoken — it under-counts by 15–20% on prose and far more on code.
"unbelievable" → 3 tokens · "北京" → 2+ · " " ws → 1
n = client.messages.count_tokens( model="claude-opus-4-8", messages=[{"role":"user", "content": big_text}], ).input_tokens # exact, model-specific, free
◆ Concept · the whole working set

What lives in the window

Context = one request's entire input
system prompt · tools · conversation history · retrieved docs · tool results · current message
Finite

Opus/Sonnet/Fable: up to 1M tokens · Haiku: 200K. Input + output share it.

Ordered matters

Models attend less to the middle — put the question near the relevant material.

Costs every call

The window is re-sent and re-billed each turn. Caching (next) softens this.

⚙ Mechanism · the illusion of memory

"Memory" is just resending

The API is stateless. A chat feels continuous only because your code re-sends the whole history every turn. That means cost grows with conversation length — turn 20 pays for turns 1–19 again.

This is exactly why caching and context-editing exist — to stop re-paying full price for the stable prefix.
msgs = [] def send(text): msgs.append({"role":"user", "content":text}) r = client.messages.create( model="claude-opus-4-8", max_tokens=1024, messages=msgs) out = r.content[0].text msgs.append({"role":"assistant", "content":out}) # ← key return out
⚙ Mechanism · the prefix rule

Caching is a prefix match

The API hashes the rendered prompt in order — tools → system → messages. A cached prefix replays at ~0.1× cost. But any byte change anywhere in the prefix invalidates everything after it.

A datetime.now() in your system prompt silently kills the cache on every request.
▸ Leverage · up to 90% cheaper

Cache the big stable part

Mark stable content with cache_control. Economics: a write costs ~1.25× (5-min TTL); reads cost ~0.1×. It pays off from the second request on.

Min cacheable prefix on Opus 4.8 is 4096 tokens — shorter prefixes silently won't cache.
client.messages.create( model="claude-opus-4-8", max_tokens=1024, system=[{ "type":"text", "text": big_policy_doc, "cache_control":{"type":"ephemeral"}, }], messages=[{"role":"user","content":q}], ) # verify: resp.usage.cache_read_input_tokens # > 0 ✓
▸ Leverage · the "M" in CALM

Three ways to manage a growing window

ToolWhat it doesUse when
Context editingClears stale tool results / thinking blockslong tool-heavy runs; old results irrelevant
CompactionSummarizes earlier history server-sideconversation nearing the window limit
MemoryPersists facts to files across sessionsstate must outlive one session (→ Module 4)
Editing prunes, compaction summarizes (risking lost detail), memory persists. Long agents use all three.
✕ Pitfalls · silent invalidators

Why your cache hit-rate is zero

Moving values

datetime.now() / UUIDs early in the prompt change the prefix every call.

Unsorted JSON

json.dumps(d) without sort_keys=True → different bytes each time.

Varying tool set

Tools render at position 0 — add/remove/reorder and the whole cache dies.

Per-user prompt

Interpolating a user ID into system kills cross-user sharing.

Diagnose: if cache_read_input_tokens is always 0, diff the rendered bytes of two requests.

Module Four

Context vs Memory

StatelessStatefulPersistentExternal / RAG
◆ Concept · the key distinction

RAM versus hard disk

ContextMemory
LifespanOne request onlyAcross calls & sessions
LivesInside the promptOutside — files / DB / vectors
Held bySent every callYou store & reload it
Cost modelTokens, every timeStorage — load only what's relevant
Every "memory" becomes context the instant you load it back into a prompt. Memory is a you problem, not a model feature.
⚙ Mechanism

You build the state

The model is a pure function: same input → (roughly) same output, no side effects, no recall. Statefulness is a wrapper you write — hold the history, persist facts, reload them.

A ConversationManager that appends every turn is the simplest stateful layer.
class Conversation: def __init__(self, system): self.msgs, self.system = [], system def send(self, text): self.msgs += [{"role":"user", "content":text}] r = client.messages.create( model="claude-opus-4-8", max_tokens=1024, system=self.system, messages=self.msgs) ... # append assistant, return
▸ Leverage · scale past the window

Store everything, retrieve a little

External memory keeps knowledge in a vector DB / files, and pulls only the top-k relevant chunks into context per query — RAG. Solves both finite-context and freshness.

Claude also has a first-class memory tool (a /memories file directory) it reads/writes across sessions.
Vector DB / files
all your knowledge
↓ retrieve top-k for this question
Context this call
system + top-k chunks + question
↓
Claude
grounded, cited answer
✕ Pitfalls

Memory that bites

✕Danger

  • Storing secrets / API keys / passwords in memory — they replay into every future context
  • Persisting PII without checking GDPR / CCPA
  • Unbounded history → context overflow + runaway cost
  • Trusting stale memory as current fact

✓Do

  • Keep secrets in a vault, never in prompts/memory
  • Per-user memory dirs + access control
  • Summarize / expire old memory
  • Timestamp facts; re-verify before acting

Module Five

Giving Claude hands

The loopSchemaTool runnerParallelServer tools
◆ Concept

The model only makes text

To touch the real world — live data, exact math, APIs, databases, sending mail — Claude emits a request to call a tool. Your code runs it and returns the result. Claude never executes anything itself.

This split is the whole security model: you decide what tools exist and gate the dangerous ones.
Claude
"call get_weather(Paris)"
↓ your code executes
Your app
real weather API → 18°C
↓ return tool_result
Claude
"It's 18°C and clear in Paris."
⚙ Mechanism · the real wire format

tool_use → tool_result

When Claude wants a tool, stop_reason is tool_use and content holds a tool_use block (name + input + id). You run it, then append a tool_result keyed by that id. Loop until end_turn.

Always append the full response.content back — it carries the tool_use block Claude needs to see.
while True: r = client.messages.create( model="claude-opus-4-8", max_tokens=2048, tools=tools, messages=msgs) if r.stop_reason == "end_turn": break msgs.append({"role":"assistant", "content":r.content}) results = [] for b in r.content: if b.type == "tool_use": out = run(b.name, b.input) results.append({"type":"tool_result", "tool_use_id":b.id, "content":out}) msgs.append({"role":"user","content":results})
▸ Leverage · the description IS the router

Write the description for selection

Claude picks tools from their name + description. Be prescriptive about when to call it, not just what it does. Add strict: true + additionalProperties: false to guarantee valid arguments.

Control choice with tool_choice: auto (default) · any · {type:"tool",name} · none.
{ "name":"search_orders", "description":"Look up a customer's orders. Call this whenever the user asks about order status or history.", "strict":true, "input_schema":{ "type":"object", "properties":{"email":{"type":"string"}}, "required":["email"], "additionalProperties":false, }, }
▸ Leverage · skip the hand-written loop

Let the SDK drive the loop

The tool runner calls the API, executes your functions, feeds results back, and repeats until done — you just write the tool functions. It still exposes per-turn hooks for approval gates and retries.

Drop to a manual loop only when you need control the runner doesn't expose (custom transport, avoiding the beta dependency).
from anthropic import beta_tool @beta_tool def get_weather(city: str) -> str: """Current weather for a city.""" return lookup(city) runner = client.beta.messages.tool_runner( model="claude-opus-4-8", max_tokens=2048, tools=[get_weather], messages=msgs) for msg in runner: # loop handled for you ...
⚙ Mechanism · faster, if independent

Many tools in one turn

One assistant message can contain several tool_use blocks (default on). Run them concurrently — but you must return all the tool_result blocks in a single user message.

Splitting results across multiple messages silently trains Claude to stop calling tools in parallel.
# Claude asks for 3 cities at once results = [ {"type":"tool_result", "tool_use_id":b.id, "content": run(b.name, b.input)} for b in r.content if b.type == "tool_use" ] # ALL results, ONE user message ↓ msgs.append({"role":"user", "content": results})
▸ Leverage · tools you don't have to run

Batteries Anthropic hosts

Web search / fetch

Fresh info past the cutoff, with citations. Runs server-side — just declare it.

Code execution

Sandboxed Python for exact math, data, charts. No client loop.

MCP connector

Reach a remote MCP server directly from the API (→ Module 6).

Memory tool

A /memories directory Claude reads & writes across sessions.

Server tools have no client-side execution — declare them in tools and results arrive as content blocks. A long server-tool turn may pause with stop_reason: pause_turn — re-send to resume.
✕ Pitfalls · SPIDER for tools

Isolate · Detect · Recover

✕Wrong

  • Giving one broad tool (raw bash) that can do anything, ungated
  • Trusting tool output blindly
  • Dropping a failed tool result instead of returning it
  • No loop cap → infinite tool loops

✓Right

  • Least-privilege, action-specific tools; gate irreversible ones
  • Validate every result before acting on it
  • Return failures with is_error: true so Claude can retry
  • Cap iterations (max_iters)

Module Six

MCP — the USB-C for AI

N×M problemClient/serverPrimitivesConnector code
◆ Concept · one protocol

Kill the N×M problem

Before MCP, connecting N AI apps to M tools meant N×M bespoke integrations. MCP is one open protocol (JSON-RPC) so any client can plug into any server — write once, connect to many. Exactly like USB-C replaced a drawer of chargers.

Any MCP-compatible client (Claude Desktop, Claude Code, IDEs, the API connector) speaks to any MCP server.
⚙ Mechanism · client ↔ server

◆ Concept · what a server exposes

Resources · Tools · Prompts · Sampling

Resources

Read-only data

Files, DB rows, docs the server can hand over as context. Like a GET.

Tools

Actions

Functions with effects the model can invoke. Like a POST.

Prompts

Templates

Reusable, parameterized prompt recipes the server offers.

Sampling

Borrow the LLM

The server asks the client's model to run a completion — client stays in control & can require approval.

✕ Pitfalls · servers are trust boundaries

Transport, auth & security

Transport

stdio for local subprocess servers; HTTP / SSE for remote. Same protocol either way.

Auth

Remote servers use OAuth / bearer tokens. Keep credentials in a vault — never in the prompt.

Security

Least privilege, validate inputs, approve sensitive tools, beware prompt-injection via returned data.

An MCP server can return text that looks like an instruction. Treat every server as a trust boundary (SPIDER · Isolate).
▸ Leverage · the MCP connector

Two halves, always together

The API can connect straight to a remote MCP server. You must pass both mcp_servers (the connection) and a matching mcp_toolset in tools — omitting either is a validation error.

In Claude Code you add servers via config instead — same protocol, no code.
client.beta.messages.create( model="claude-opus-4-8", max_tokens=1024, betas=["mcp-client-2025-11-20"], mcp_servers=[{ "type":"url", "name":"github", "url":"https://.../mcp/"}], tools=[{"type":"mcp_toolset", "mcp_server_name":"github"}], messages=msgs, )

⚙ Mechanism · it's the tool loop + a cap

An agent is the tool loop

There's no magic — the agent loop is the same while stop_reason == "tool_use" loop from Module 5, bounded by a hard iteration cap so it can never spin forever.

Give it thinking (adaptive) + a generous effort so its planning is good, not just fast.
MAX = 12 for step in range(MAX): r = client.messages.create( model="claude-opus-4-8", max_tokens=4096, output_config={"effort":"high"}, tools=tools, messages=msgs) if r.stop_reason == "end_turn": break # goal met ... run tools, append results ... else: escalate("hit max iterations") # recover

✕ Pitfalls

Where agents go rogue

✕Failure modes

  • Infinite loops (no iteration cap)
  • Acting on hallucinated / bad tool data
  • Irreversible actions with no human gate
  • Scope creep — one agent trying to do everything
  • Runaway cost from high effort × long loops

✓Guardrails

  • Hard max_iters + task budget
  • Validate results; distrust surprising ones
  • Approval gate on spend / delete / send
  • One responsibility per agent
  • Tune effort to the task, not always max

⚙ Mechanism · four real reasons

Not just speed — clean context

Specialization

Each subagent has one job + only the tools it needs (SPIDER · Scope).

Context isolation

Each gets a clean window — no overflow, no cross-contamination of the main thread.

Parallelism

Independent subtasks run at once — the win for research & big sweeps.

Containment

One subagent failing doesn't poison the whole run.

Bonus: subagents dodge a caching gotcha — instead of switching models mid-thread (which kills the cache), spawn a subagent on the cheaper model.
▸ Leverage · four shapes

Router · Pipeline · Parallel · Orchestrator

Router

Classify the request, hand to the right specialist. (Support triage.)

Pipeline

Chain stages, each output feeds the next. (Extract → analyze → format.)

Parallel / fan-out

Many independent workers at once, then merge. (Research, audits.)

Orchestrator-worker

Lead plans sub-questions, spawns workers, synthesizes. (Research system.)

Dependent work stays sequential (pipeline); only truly independent work fans out.
✕ Pitfalls

The cost of a crowd

✕Watch out

  • More agents = more tokens & coordination overhead
  • Aggregation is the hard part — merging is where quality is lost
  • Spawning subagents for trivial, sequential work
  • Duplicated effort when tasks overlap

✓Do

  • Use subagents for big, parallel, or isolation-needing jobs only
  • Give the synthesizer a clear dedupe + merge spec
  • Keep single-file / sequential work in the main agent
  • Scope each subtask so they don't overlap

The four decisions

Which model?

Hard/long-horizon → Opus 4.8 (or Fable 5). Volume/coding value → Sonnet 5. Simple/fast → Haiku 4.5.

Cache or not?

Large stable prefix reused ≥2× → cache. Prefix changes every call → don't (pure write cost).

Tool vs MCP?

One-off, in-process → a plain tool. Reusable across apps / external system → an MCP server.

Agent or not?

Fixed steps → workflow. Open-ended, model-driven, recoverable errors → agent.
